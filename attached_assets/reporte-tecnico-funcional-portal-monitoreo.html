Portal de Monitoreo Financiero-Fiscal para Productores

Estado evaluadoMVP funcional / ambiente de desarrollo
PropósitoAlcance, arquitectura y preparación para AWS

1. Resumen ejecutivo

La solución es un portal web para concentrar el monitoreo financiero, fiscal y operativo de productores agrícolas. Permite identificar riesgos, generar alertas, consultar expedientes de productores y administrar reglas de evaluación desde una interfaz con controles por rol.

El producto actual es un MVP navegable y funcional con datos de demostración. La capa de negocio, las reglas, la autenticación y los módulos de consulta ya están implementados; sin embargo, la persistencia local, los adaptadores externos simulados y la operación programada en proceso impiden liberarlo todavía como un sistema productivo multiusuario y escalable.

Conclusión de preparación: no se recomienda publicar el estado actual directamente a producción. Se requiere, como mínimo, sustituir el archivo JSON por una base de datos administrada, implementar integraciones reales, endurecer seguridad/autorización, automatizar despliegues y habilitar observabilidad y respaldos.

2. Alcance funcional actual

Visión y seguimiento

  • Dashboard con indicadores de productores, alertas críticas, productores en riesgo y tareas pendientes.
  • Gráficas y distribución de información por zona/distrito y cultivo.
  • Consulta de alertas recientes y estado general de cumplimiento.

Expediente del productor

  • Listado de productores con filtros y paginación.
  • Ficha de detalle con cultivo, distrito, datos del productor, domicilio fiscal y contactos.
  • Pestañas de razones sociales, ranchos, cultivos, datos financieros y alertas relacionadas.

Alertas y exportación

  • Listado con filtros por severidad, zona/distrito y estado de resolución.
  • Resolución de alertas por usuarios autorizados.
  • Exportación CSV de alertas y datos del productor; incluye BOM UTF-8 y Content-Type UTF-8 para apertura correcta en Excel.

Diagnóstico y reglas

  • Validaciones SAT, IMSS, financiera y legal, individuales o como diagnóstico completo.
  • Motor de reglas configurable: umbrales, booleanos y reglas personalizadas.
  • Administración de reglas y ejecución manual del monitoreo programado.

Procesos de negocio cubiertos

  1. Registro y consulta de la información del productor y sus entidades relacionadas.
  2. Ejecución de validaciones sobre cumplimiento fiscal, IMSS, información legal y métricas financieras.
  3. Evaluación de resultados mediante reglas y generación de alertas.
  4. Seguimiento y resolución de alertas por el equipo autorizado.
  5. Consulta ejecutiva en dashboard y reportes; exportación de resultados a CSV.

3. Arquitectura actual (“as is”)

La aplicación está construida como un monolito web con Next.js 14 (App Router), React 18 y TypeScript. La misma aplicación entrega la interfaz y expone las rutas API. El estilo visual usa Tailwind CSS y los gráficos se presentan con Recharts.

5. Arquitectura propuesta para AWS (“to be”)

Se recomienda conservar Next.js como aplicación principal, pero desplegarlo como un contenedor inmutable y separar las cargas web, programadas y asíncronas. La siguiente topología permite crecer sin rehacer el producto:

INTERNET │ CloudFront ── AWS WAF ── Application Load Balancer │ ECS Fargate: servicio web Next.js │ ┌───────────────┬───────┴────────┬─────────────────┐ ▼ ▼ ▼ ▼ RDS PostgreSQL ElastiCache* S3 (exportables) Secrets Manager Multi-AZ cache/rate limit / documentos + KMS │ ├── AWS Backup (copias y restauración) └── CloudWatch / CloudTrail / GuardDuty / Config EventBridge Scheduler ──► SQS ──► ECS Fargate Worker │ └── APIs SAT / IMSS / financieras / legales Git repository ──► CI/CD ──► ECR ──► ECS (dev / staging / producción)

Objetivo AWS ECS Fargate simplifica la operación del monolito Next.js sin administrar servidores. Si el volumen inicial es bajo, puede comenzar con una sola tarea web en un entorno no crítico; producción debe usar al menos dos tareas distribuidas en zonas de disponibilidad y base de datos Multi-AZ.

6. Insumos necesarios para liberar a producción

Definiciones de negocio

  • Catálogo definitivo de productores, razones sociales, ranchos, cultivos, estados de cumplimiento y reglas de decisión.
  • Matriz de permisos por perfil, incluyendo el vínculo verificable entre cuenta de productor y su expediente.
  • Flujo de alerta: severidades, responsable, SLA, comentarios/evidencias, escalamiento y criterios de cierre.
  • Fuentes oficiales de datos: proveedores, contratos, ambientes de prueba, límites de consumo y responsables de cada integración.
  • Política de conservación de datos, auditoría, privacidad y requisitos regulatorios aplicables.
  • Volumetría esperada: productores, validaciones diarias, usuarios concurrentes, tamaño documental y objetivo de disponibilidad.

Insumos técnicos y de seguridad

  • Cuenta AWS separada por ambiente (desarrollo, pruebas/staging y producción), región aprobada y diseño de red VPC privada en varias zonas.
  • Dominio productivo, certificados TLS en ACM, DNS en Route 53 y reglas de WAF acordadas.
  • Credenciales de integración gestionadas en Secrets Manager; cuentas demo eliminadas y secretos rotados.
  • Modelo PostgreSQL, estrategia de migración desde el dataset actual, índices, retención de backups y prueba de restauración.
  • Repositorio con CI/CD, escaneo de dependencias, análisis estático, construcción de imagen, pruebas y aprobación antes de producción.
  • Política IAM de mínimo privilegio, cuentas de operación, bitácora de auditoría y gestión de accesos de emergencia.
  • Tableros, alarmas y runbooks: error de aplicación, latencia, consumo de base de datos, fallas de cola, validaciones y disponibilidad.

8. Criterios mínimos de liberación

La liberación debe aprobarse únicamente cuando:
  • La información operativa esté en PostgreSQL con respaldos y una restauración probada.
  • Las cuentas demo y credenciales expuestas hayan sido eliminadas, rotadas o sustituidas por identidad corporativa/MFA.
  • Todo productor sólo pueda consultar sus propios datos, y las acciones administrativas estén auditadas.
  • Las integraciones reales tengan manejo de errores, reintentos, límites y trazabilidad.
  • Las validaciones recurrentes corran fuera del proceso web, sin duplicar ejecuciones ni perder trabajos.
  • Existan pruebas automatizadas, pipeline de despliegue, monitoreo, alertas y runbooks operativos.
  • Se hayan ejecutado pruebas funcionales, de seguridad, carga y recuperación ante fallas con resultados aceptados.
Documento basado en la revisión del código y configuración disponibles en el entorno de desarrollo.
